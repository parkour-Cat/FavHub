# FavHub 丰富流水线（摘要/标签/内容类型）

对 FavHub 待丰富队列做 拉取 → 生成 → 提交 的循环。生成完全由 Agent 自身模型完成，FavHub 只负责校验与落盘；结果写入 `source.json` 丰富区块并渲染进 `content.md`，随后自动重新入索引，可被 FTS/混合检索命中。

## 必须先告知用户

- 摘要与标签**由 Agent 模型生成**（记录 provider/model），内容会被本会话的模型读取；
- 用户可**随时停止**本流程或完全跳过丰富——不丰富不影响采集数据与原文检索；
- 已有的丰富结果在内容变化后会重新生成，用户 `notes.md` 永不改动。

### 启动前确认摘要需求

每次用户请求启动本 skill 的丰富流程时，必须先提醒用户：摘要不是采集、原文保存或原文检索的必需项。应同时说明：

- **好处**：摘要可改善条目浏览、主题发现、搜索结果展示，并帮助 FTS/混合检索命中关键语义；
- **成本**：模型需要读取本地正文、字幕或 OCR，正文越长、条目越多，消耗的输入文本量、时间和模型调用额度越多；摘要输出本身通常较短，主要成本来自输入内容；
- **选择**：用户可以选择完整处理、只处理有正文的条目、**先只做某一个平台**，或暂时跳过摘要。

在用户明确选择前，不得直接开始大批量摘要任务；如果用户选择跳过，应停止摘要流程，不影响采集数据、原文保存和原文检索。

### 先买一小片再决定

成本按条目算，而各平台的正文长度差一个数量级——同一批待办里，X 的中位数是几百字符，GitHub README 是几万。**给出估算的同时应当建议先跑最便宜的那个平台**，用真实数字代替估算再决定要不要继续：`favhub.enrich_next` 接受可选的 `platform`，只认领该平台的任务。

**决不**用 `favhub.enrich_skip` 来"跳过不想做的平台"——skip 是给内容确实无法概括的条目用的，拿它筛平台等于对着没人拒绝过的条目记下一次拒绝。

## 工作流程

### 0. 预检

1. `favhub.status` 确认 MCP 可达；
2. 报告当前待丰富任务数（`enrichment_pending` 含索引任务，实际数量以逐条拉取为准）；若需要为存量条目补队列，提示用户先运行 `favhub --root <root> enrich-backfill`。

### 1. 循环：拉取 → 生成 → 提交

对每条任务（`favhub.enrich_next` 返回 `task` 为 null 时结束；带 `platform` 时 null 只表示**该平台**做完了，别据此宣称整个队列清空）：

1. 读取任务给出的 `title`/`author`/`canonical_url` 与全部系统内容（content.md、transcript、ocr）；`truncated: true` 时内容被截断，摘要中必须注明"内容较长，摘要基于开头部分"。
2. 生成结果，规则固定：
   - **摘要**：中文，3-6 句，≤ 2000 字符；嵌入原文**关键术语**（如 codex、RAG、hybrid retrieval 保留英文原词），让中英文搜索都能命中；不得虚构内容中没有的信息。
     - **必须显著短于原文，目标 ≤ 50%。** 正文超过 200 字符时，摘要长度 ≥ 原文会被 `enrich_submit` 直接拒绝——不比原文短的东西不是摘要，是换个说法重写一遍，读者一无所得而生成开销照付。实测全库有 17% 的历史摘要犯了这个错。
     - **短正文（≲400 字符）不要复述**，写一句话点题即可。这类条目的价值几乎全在**标签**上：原文本来就比摘要好读，而标签是检索用的分面。长内容（GitHub README、知乎长文、B 站字幕）才是摘要真正创造价值的地方——实测压缩比 0.03–0.05，那是把几万字变成几百字。
   - **标签**：3-8 个自由标签，小写归一（提交时会再次归一去重），中英混合允许；覆盖主题、领域与关键工具名。
     - **决不把中文词音译成拼音。** 闲鱼就写 `闲鱼`，不是 `xianyu`；副业就写 `副业`，不是 `fuye`。英文原名的工具和概念（`cursor`、`claude`、`rag`、`nft`）保留英文，那是它们本来的名字，不是音译。中文内容以中文为主时，`enrich_submit` 会**拒绝一个中文标签都没有的提交**。
     - 理由是检索：没人会搜 `xianyuuyu`。实测某批便宜模型产出的标签有 46% 是拼音且多处拼错，而短条目的价值几乎全在标签上。
   - **内容类型**：按主载体判定——B 站视频条目为 `video`；X 纯文本为 `text`；以图片为主的为 `image`；图文/视频混合叙述为 `mixed`。
3. `favhub.enrich_submit`（`taskId` + summary/tags/contentType/provider/model）。
   - 返回 `outcome: "applied"`：继续下一条；
   - 返回 `outcome: "stale"`：条目内容已更新、任务已被替代，直接继续下一条（新任务会自动出现在队列里）。
   - **被拒绝**（摘要不比原文短 / 中文内容没有中文标签 / 正文无可摘要内容）：任务仍在你手上、状态不变，**修好后重新提交同一个 `taskId`**。决不因为被拒就改用 `enrich_skip`——那是把质量问题伪装成内容问题。
   - **拒绝信息会明说是哪条规则，照着改，别靠试。** 有一条规则的答案不是改写而是跳过：`no readable content to summarise` 指正文去掉 URL 后为空，此时唯一正确的动作是 `content_unsupported`。**同一个 `taskId` 改过两次仍被拒就停下**，把拒绝原文报给用户——继续换字数、换标签、换 provider 试是在猜，实测有一轮这样试了 15 次仍失败，最后把规则拒绝误报成"工具坏了"。
4. 生成失败（内容为空、无法理解、模型输出异常）：调用 `favhub.enrich_skip`，继续下一条。**两个 code 的后果不同，别混用**：
   - `generation_failed` —— 这次没弄出来（模型输出异常、超时）。任务回到 pending 可重试，返回 `outcome: "retryable"`。**它会再次被认领**，所以别拿它当"跳过这条"用，否则下一次 `enrich_next` 原样递回来，整轮卡死在同一条上。
   - `content_unsupported` —— 对**这份内容**的判断（正文为空、只有一个短链、纯噪声）。任务转入 `declined` 退出队列，返回 `outcome: "declined"`。内容变了会按新的 `input_hash` 自动重新入队，所以这不是永久判决。
   - **但"有内容"不等于"有链接"。** 正文去掉 URL 后剩不下几个字时，这条**没有任何可摘要的东西**，必须 `content_unsupported` 跳过。决不写"这是一条分享链接的推文"这种什么都没说的摘要——它比跳过更糟：跳过至少诚实，这个是往库里塞噪声，而且极易滑向编造（真实案例：正文只有一个短链，摘要却写成了"X post about AI, ads and apps"）。服务端会拒绝这类提交。
   - **部分内容不可用时，用可用的那部分，不要整条跳过。** 一个条目可能同时有简介和字幕，而其中一份是坏的——字幕是语音识别噪声，或者干脆是别的视频的。这时**只要还有一份能读，就必须出摘要**，并在摘要里说明依据的是哪部分（如"依据视频简介，字幕内容与本视频无关"）。真实案例：有两条 B 站条目的简介有近三千字、把教程讲得清清楚楚，却因为字幕对不上被整条 declined 掉了，而 declined 是**永久退出队列**的。
   - **跳过判据严格**：FavHub 是用户私人收藏的镜像（非对外发布），只有**全部内容**都为空、失效链接、或纯噪声无可提取信息才跳过。决不因为话题非技术、敏感、涉及灰产/争议观点/个人闲聊就拒绝——如实中立地概括它讲了什么即可（闲聊性质仍打 `纯娱乐` 标签并给摘要）。误跳过会让收藏内容永久缺失检索入口。

### 2. 生成一律走便宜模型（默认，不是优化项）

**摘要和打标签必须交给便宜档模型生成**，主会话只做编排、格式校验和抽查。这不是"任务多的时候才考虑"——摘要是一个读一段文本、写三五句话的活儿，用主会话的强模型做，单价高出一个数量级而质量差别对不上这个价钱。

**本 Skill 同时装给 Claude Code 和 Codex，规则按"档位"而不是型号名理解**：用你所在运行时**最便宜的、能胜任"读一段文字写三五句"的那一档**，并用该运行时的子代理/子任务机制派发。Claude Code 侧 haiku 级即可胜任；Codex 侧取其对应的低价档。型号会变，"别用编排模型去做摘要"这条不会变。

主会话直接生成只有两种情况可以：**单条**（用户点名某一条），或**抽查复核**时对照原文重写一份做比较。

`model` 字段必须**如实记录**实际生成模型，决不冒充更强模型，也不要为了省事填运行时默认值；用便宜模型生成却记成主会话模型，会让后续的质量追溯完全失效——那正是判断"便宜档够不够用"的唯一依据。

### 3. 批量模式（待办任务多时的标准做法）

待丰富任务超过约 20 条时，按批组织：

1. 分批认领任务并导出内容（每个子代理按内容总量分配，约 ≤10 万字符）；
2. 并行派出子代理生成结果（规则与上文完全一致），主会话校验格式后统一提交；
3. **抽查义务**：首批（约 50 条）由主会话对至少 10% 的结果对照原文抽查（摘要忠实、
   标签合理、关键术语保留、**长度确实比原文短**）；质量不达标则调参重跑该批，达标后放量；
4. 分流：内容特别长或多语言混杂的条目可路由给更强模型；生成失败照常
   `favhub.enrich_skip`，不因个别失败中断整批。

标签约定：纯音乐、鬼畜、搞笑段子等无知识内容的条目，额外打 `纯娱乐` 标签，
方便检索侧按标签排除；判断存疑时不打，宁缺勿滥。

### 4. 进度报告

每处理 5-10 条向用户报告一次进度（已完成/跳过/剩余估计）；用户可随时停止，已提交结果不受影响。

## 边界

- 只通过三个 MCP 工具操作；不直接读写数据目录文件。
- 摘要/标签只基于任务提供的内容；不访问外部网络补充资料。
- 决不能以 fixture 测试或假 Agent 结果宣称真实丰富质量；真实运行的质量由用户抽查确认。
