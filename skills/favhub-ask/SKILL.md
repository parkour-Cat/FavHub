# FavHub 检索使用

用本地 MCP 检索工具查询用户的个人收藏库，把命中的收藏作为**个人参考资料**融入回答，并给出可追溯引用。

## 核心纪律（v0.1 设计 §6）

1. **FavHub 是个人参考资料，不是唯一事实来源。** 技术版本号、平台规则、价格等**易变**内容，必须用当前外部资料校验后再下结论；收藏里的内容反映的是收藏那一刻的状态。
2. **回答必须区分来源**：明确标注哪些信息"来自个人收藏"（附引用）、哪些"来自当前外部资料"或模型自身知识。
3. **查不到就明确说未找到**，不得把弱相关片段强行拼接成看似有依据的回答。

## 工作流程（按顺序执行）

### 1. 判断是否查库（用 `favhub.collections` 决定，不靠感觉）

先把问题归类为**查找型、总结型、推荐型、对比型或方案型**，再按下面三类决定查不查。

**A. 明确回忆型 —— 直接检索。** 用户说"我收藏过/我存过/我记得有个视频/帮我找找我之前看的"。这类问题里库本身就是答案，不必先读地图；找不到也要如实说没找到。

**B. 任务中的个人先例 —— 先调 `favhub.collections`，按地图决定。** 写代码、选型、做方案时，用户可能早就存过他自己挑选过的资料。每个会话调用**一次** `favhub.collections` 就够，结果记住复用。读地图有两条规则：

- **收藏夹名要是一个主题才算数。** `算法`、`web3`、`图像处理`、`钢琴` 命名的是内容；`默认收藏夹`、`稍后再看`、`干货！`、`好文`、`精选`、`临时`、`乱七八糟` 命名的是"当时觉得该存"，条目再多也不指向任何主题。库里最大的几个收藏夹恰恰属于后者，拿它们判断主题会得到全错的结论。具名收藏夹的条目数则是可信的密度信号：几十条说明这是他长期在攒的方向，个位数说明检索一次就够、不值得反复改写查询。
- **`platforms` 里的 `unfiled` 是地图的盲区，不是空白。** 某平台条目全部 `unfiled`，说明它压根没有收藏夹结构（GitHub star、X 书签都是平的），于是**没有任何收藏夹名会提到它们的内容**。选库、挑工具、找轮子时 GitHub star 往往是最相关的那部分，而它在收藏夹列表里完全看不见——这种情况不要因为"没有匹配的收藏夹"就跳过，直接按主题检索并带上 `platforms: ["github"]`。

**C. 一般知识问题 —— 不查。** 与"用户存过什么"无关的问题（如"Python 的 GIL 是什么"），查库只增加延迟和噪声。

**任务模式（B）到此为止，不要往下走完整流程。** 命中了就用一两句话说明"你收藏里有 X"并附链接，让用户自己决定要不要展开；下面第 3–4 步的全文精读与证据矩阵是**回答模式**的要求，在任务途中执行只会把活儿打断成检索报告。也不要因为某个收藏夹名字对得上，就去检索用户根本没问的东西。查不到不能靠猜测补齐。

### 2. 主题查询与检索（`favhub.search`）

- 以用户原话和 1–2 个**中英**、宽窄改写查询，保留 `platforms`、`publishedSince`、`publishedUntil`、`limit` 等必要过滤器。
- 主题正好落在某个**具名**收藏夹里时可传 `collections: ["算法"]` 收窄到用户亲手归过档的那批；但只在地图确认该收藏夹存在时用，且不要用它排除 `unfiled` 平台上的内容。
- 区分**主题查询**和**主要载体**：问“AI 视频相关内容”不传 `contentTypes`；只有问“只看收藏的视频”才传 **`contentTypes: ["video"]`**。不得因搜索结果暂时稀少就擅自把主题查询改成载体过滤。
- 结果中的 `retrieval_mode`、匹配来源、摘要与**标签**只是定位线索，不能直接当作完整事实。

### 3. 选择不同收藏的证据

按证据强度从**不同收藏**选择前 3–5 个不同收藏，优先含 `body`、`transcript`、`ocr` 或 `mixed` 的命中。检查 `evidence_level`、`evidence_warning`、`supporting_chunks`；同一条目的重复 chunks 不得挤掉其他收藏。对所选前 3–5 个不同收藏必须**逐一**调用 `favhub.get_item` 并设 `includeContent: true`，**每个**都要读取全文（正文、字幕或 OCR）；搜索摘要/excerpt 不能代替全文。

### 4. 建立证据矩阵并综合

在内部建立**证据矩阵**，至少记录：来源、具体步骤、工具、前置条件、限制、证据等级、时效风险。合并多个来源的共识、互补信息和冲突，再生成直接回答、比较或实践路线；最终答案**不是搜索结果列表**。明确哪些是收藏事实、哪些来自当前外部资料，哪些是 **Agent 综合推断**。

### 5. 引用与结论纪律

每条来自收藏的信息给出：

- 稳定引用 `citation_id`（形如 `favhub:bilibili/BV…#chunk-3`）；
- **原链接**（`canonical_url`），视频内容尽量带**视频时间戳**（transcript 片段的 `[HH:MM:SS]` 可直接换算）；
- 本地路径（`local_path`，数据根相对路径）便于用户翻看原文与自己的 notes.md。

**来自收藏的实质性主张**必须同时给出对应的 `citation_id`、`canonical_url` 和 `local_path`，并标注“来自个人收藏”。来自当前外部资料的实质性主张必须同时给出**具名外部来源和外部 URL**，并标注“来自当前外部资料”。推断出的结论必须标注“Agent 综合推断”；**不伪造**、不冒充 FavHub `citation_id` 来覆盖外部或推断主张。若推断基于收藏，分别引用支撑它的收藏事实，而不是给推断本身捏造 FavHub 引用。`title_only` 只能标为**待进一步核验的线索**，永远不能证明详细步骤、工具或效果。

证据不足时明确说未找到或仍需核验，不强行拼接结论。对实践问题还必须给出推荐顺序、操作步骤、前置条件、验证标准和风险。

### 6. 未命中

前 5 条结果与问题无实质关联时，如实说"你的收藏里没有找到相关内容"，再用外部资料或模型知识回答，并标注来源属性。

判断"没有"之前先分清是**库里确实没有**还是**索引没准备好**：`favhub.status` 的 `index_state`、待处理与失败任务数会说明这一点。索引不可用时说"现在查不了"，不要说成"你没收藏过"。

## 边界

- 只读：本 Skill 决不修改收藏库；用户笔记 notes.md 只读不写。
- 不把检索结果的存在当作事实背书——收藏的内容也可能过时或错误（提醒用户即可）。
