# 同源只读请求：扩展做什么，Agent 不做什么

知乎用同源会话鉴权，因此页面可以自己请求下一页——不需要拦截，也不需要向页面注入
任何代码。与 Bilibili 同形态，与 X 相反。

**这件事完全由 FavHub 浏览器扩展完成，Agent 不参与。** 本文档描述扩展的行为，
以便 Agent 如实向用户解释正在发生什么，而不是一份操作指南。
决不构造第三方请求、决不访问任意 URL、决不读取或导出 Cookie/z_c0 等凭证。

## 扩展请求的端点

| 用途 | 端点（同源 GET） |
| --- | --- |
| 账号标识 | `/api/v4/me` |
| 收藏夹列表 | `/api/v4/people/<标识>/collections`（`offset` 递增） |
| 收藏夹条目 | `/api/v4/collections/<id>/items`（`offset` 递增） |

这三项构成**固定白名单**，由内容脚本在发起请求前再校验一次：Service Worker 说出
一个 URL 不等于有权请求它，否则一个被攻陷的 Worker 就能把页面当作转发代理。

白名单用的是**锚定模式**而不是前缀，因为知乎把标识放在路径里：
`/api/v4/collections/` 作为前缀会连带放行同一收藏夹上的相邻写操作端点，
`/api/v4/me` 作为前缀会放行整个账号下的一切。扩展也只发 GET。

## 唯一的终止信号

`paging.is_end` 是唯一判终依据。被删条目会让**中间页**的条数少于每页上限，
所以短页是正常现象。把短页当终点会静悄悄地截断扫描，然后把 frontier 推到
它从未看到的位置——结果看起来是一次干净成功、只是库小了很多的同步。

同理：空页若 `is_end` 为假也要继续；缺少 `paging` 块的响应按 `page_changed`
拒绝，而不是当作安静的结束。`totals` 仅供展示。

## 条目 ID 的一致性

扩展算出的条目 ID（`{type}-{id}`）必须与 FavHub 侧 `zhihu_mapping.source_id_for`
完全一致。拼错不会报错，只会让 frontier 永远匹配不上、每次增量都全量重扫。

## 响应形状

冻结样例见仓库 `tests/fixtures/zhihu/`；实际解析一律交给 FavHub 纯解析器
（`favhub.zhihu_parsers`），错误信封返回稳定错误码，决不当作空列表。
回答标题取问题标题；文章用自身标题；pin/zvideo 等未支持类型降级保留标题、
摘要与链接，决不让单条掐死整页。

## 脱敏规则

- 只提交响应**正文**中的业务字段；不得附带请求头、响应头或任何会话凭证。
- 日志与进度报告只写：计数、稳定错误码、收藏夹 ID/名称、条目 ID；决不粘贴原始响应全文。
- 作者公开信息可以保留；观看者自身身份信息不得写入任何条目或日志。

## 与真实会话探针的关系

仓库中的 fixture 为脱敏样例；只有真实会话冒烟通过后才能宣称连接器可用。
